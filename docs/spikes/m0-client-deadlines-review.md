## Snapshot and verdict

Reviewed the Claude-written fix at **`6850c0fe196cfba25174c25c1bdb97222617a0f1`**, parent **`1d3c409514dc30a774376d7cdc124a6069c843c4`**, on `review/m0-bounds`. This review covers only the IPC client deadline follow-up from the original `docs/spikes/m0-durable-core-code-review.md` on `integration/m0-e2e`. I read the actual diff, surrounding transport and job call sites, the new tests, and `spikes/m0-durable-core/CLIENT-DEADLINES-REPORT.md`. No runtime or test source was changed for this review.

**Verdict: approve this bounded IPC transport fix, with the qualifications below.** The single cancellation source bounds connect, hello exchange, request socket write/flush, and response read. Once the request write is entered, transport failure, EOF, malformed response, deadline, and caller cancellation report `outcome_unknown`; the client does not retry. A cancellation after the real server handler received a request closes only the client connection; the handler remains tied to daemon lifetime. This is sufficient for the original connect/write deadline follow-up. It does not certify a strict wall-clock bound for every part of `SendAsync` or approve the inherited core.

**Inherited blocker remains open:** the admission/dispatcher halt race **F1** at `1d3c409`, documented in `docs/spikes/m0-core-fault-fix-code-review.md` on `integration/m0-e2e`, is under another writer. Neither this fix nor its passing gates resolves it. No approval of `1d3c409` or the full durable core is implied.

## Review observations and qualifications

1. `IpcClient.cs:48-74` starts one budget after reading the credential, uses it for connect, hello, request write, and response read, and disposes the socket when it expires. `Frames.cs:10-18` writes header/body and flushes with that token; `Frames.cs:20-66` reads under the same parent token. The tests cover stalled hello, stalled response, a physically stalled large request write, and two steps whose combined duration exceeds the budget. The published native scenarios cover the changed client on normal paths, not a stalled native client.
2. `IpcClient.cs:66-74` marks uncertainty **before** entering the request writer. That is deliberately conservative: an error or caller cancellation during the write cannot be reported as proof of no acceptance. The real-server cancellation test in `IpcClientDeadlineTests.cs:119-151` waits until the request reaches the handler, cancels the caller, observes `outcome_unknown`, then observes daemon-side completion. The CLI and MCP bridge do not mint or automatically retry keys (`ClientCommand.cs:32`, `JobsMcpBridge.cs:73`). Recovery still requires an explicit same-key submission or `job_get`.
3. **Deadline scope needs precise wording.** `IpcClient.cs:47` performs synchronous `ReadPrivateFile` before starting the budget; `StateDirectory.cs:57-71` still uses an unbounded `File.ReadAllBytes`. `Frames.WriteAsync` serializes the whole request before its first token-aware stream write (`Frames.cs:10-15`), so a very large caller-supplied request can also spend time and memory outside cancellable I/O. These are not regressions in this fix. They prevent a general claim that all elapsed time in `SendAsync` is bounded. The prior review's private-file bound follow-up remains open; request-size preflight or a narrower transport-deadline claim is needed before promoting a strict full-call guarantee.
4. The before-write caller-cancellation test cancels during pre-request transport (`IpcClientDeadlineTests.cs:108-116`). Cancellation after the hello but during request serialization may be conservatively reported as `outcome_unknown` because `requestWriteStarted` is set before serialization. This is safe for durable acceptance but is more conservative than the report's literal “before any write throws” wording. No test isolates that narrow boundary. Malformed hello frames retain their existing frame error codes; the new `daemon_unavailable` classification applies to deadline and transport failures before the request write.
5. The server can still return `internal_error` after a post-commit read failure (`IpcServer.cs:123-127`, `JobsEndpoint.cs:15-22`). That is the original review's separate post-commit response ambiguity, not a client transport regression. An error response after submission must not be read as proof of no durable acceptance.
