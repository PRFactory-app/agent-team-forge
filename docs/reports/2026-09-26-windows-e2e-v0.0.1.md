# Windows e2e check of v0.0.1

This check ran on 2026-09-26 on a Windows 11 VM with 2 vCPU and 8 GB RAM. The UAC split-token is
not active on this VM, so explorer also runs at High integrity. The build is `main` `308572e`
(tag `v0.0.1`), published self-contained with `-p:PublishAot=false` (no MSVC linker on the VM),
and installed with `atf setup --mode wt --apply`. All tests except the install used throwaway
state directories. Pi is not installed.

### Evidence for the passing items

- **1:** a Medium-IL process was created with a duplicated token lowered to `S-1-16-8192`
  (`CreateProcessWithTokenW`; `whoami /groups` confirmed Medium Mandatory Level). Elevated daemon
  with a Medium client: `client list` returned `ok`. Medium daemon (`atf daemon` started from the
  lowered token) with an elevated client: `client list` returned `ok`.
- **2:** `XDG_STATE_HOME` pointed at a directory that did not exist, and a real legacy
  `%LOCALAPPDATA%\AgentTeamForge\profile.json` was present. `atf setup --mode wt` exited 64 with
  the documented error. No new directory was created, and the legacy directory was unchanged
  (15 files, identical byte count).
- **3, 4:** a Codex job in `C:\code` completed with the expected text while the Codex TUI held
  the rollout open. Claude jobs returned `ok`.
- **6:** four CPU-burn processes ran during launch. The wrapper was written at 14:06:38 and the
  PID sidecar at 14:07:18, a 40 s start. The job reached `completed`, not `needs_reconciliation`.
- **7:** a Codex job in `needs_reconciliation` (the stranded new-cwd case from A) had a live tab.
  `atf client stop` returned `stopped`, the job ended `cancelled`/`stopped`, and the tab's
  `powershell.exe` and `codex.exe` exited.

## A. wt launches block on the workspace-trust prompt in a new cwd (Windows-specific)

The unattended trust handling exists only in the Herdr paths:

- Codex: `HerdrAgentControl.cs` (around line 186) passes
  `-c projects={"<cwd>"={trust_level="trusted"}}`.
- Claude: `HerdrTerminal.cs` (around line 140) handles the workspace trust for that launch only
  (`bypassClaudeWorkspaceTrust`), and `HerdrAgentControl.cs` (around line 183) passes
  `--settings {"skipDangerousModePermissionPrompt":true}`.

`WtTabControl.cs` has none of these (Claude around line 288, Codex around line 291), with these
observed results:

- **Codex, fresh cwd:** no Codex session file was ever written. The job ran into the 180 s bound
  and went to `needs_reconciliation` / `interactive_delivery_not_confirmed`.
- **Claude, fresh cwd:** the job only completed after the operator pressed OK in the tab.
- **Claude bypass warning:** not observable on this machine, because the user's
  `~/.claude.json` already contains `skipDangerousModePermissionPrompt: true`. The wt path does
  not pass the `--settings` override the Herdr path uses, so on a clean profile it would most
  likely show the warning.

Suggested fix: move the per-launch trust and bypass arguments into shared launch-arg
construction that both `HerdrAgentControl` and `WtTabControl` use, and cover the wt argv in
`WtInteractiveBackendTests`. Watch the PowerShell wrapper quoting of the TOML key for Windows
paths with backslashes.

## B. Access denied on the pipe crashes the client instead of printing a clear error

A Low-IL client (`S-1-16-4096`) against a running daemon printed
`Unhandled exception. System.UnauthorizedAccessException: Access to the path '...\start.lock' is denied`
with this call path:

`ClientCommand.EnsureDaemonAsync` → `SetupCommand.StartAsync` → `AcquireStartGateAsync` → `DaemonLock.TryAcquire`

The client treats a refused pipe connection as "daemon not running" and tries to start one. A
Low-IL client is contrived, but the same path applies to any real authorization failure (for
example a wrong pipe owner). Suggested fix: when the pipe exists but connecting is denied, report
`access_denied` with a short explanation, do not try a lazy start, and catch
`UnauthorizedAccessException` around the start gate.

## C. Web console never starts on Windows

Every daemon start on Windows logs:

`web console unavailable on 127.0.0.1:8765: PlatformNotSupportedException: Unix file modes are not supported on this platform.`

The likely cause is `WebConsoleToken.cs:66`: `UnixCreateMode = OperatingSystem.IsWindows() ? null : ...`.
On .NET 11 RC1 that setter throws on Windows even when it is set to `null`. Use `PrivateFiles.Options`
(`src/AgentTeamForge.DAL/Files/PrivateFiles.cs`) like the other call sites do. A grep for any
other remaining `UnixCreateMode =` assignments is worthwhile.

## D. Minor findings

- **Misleading lazy-start error:** when the daemon exits during startup (here because of
  `wt mode requires an agents profile`), the client prints
  `daemon could not start: Process was not started by this object, so requested information cannot be determined.`
  That comes from reading process information on a process the client did not start. It should
  show the daemon's own error or point to `daemon.log`.
- **Pre-release rows:** a state directory written by builds before v0.0.1 returns
  `internal_error` from `client get` on old jobs, and `outcome_unknown` from `client list` once
  the page reaches those rows. The daemon log only says `client connection dropped`. No
  migration is needed, but the error should be logged instead of dropping the connection.
- **Version:** a local publish reports `atf 1.0.0`, not `0.0.1`. The version only seems to be
  stamped by the release script.
