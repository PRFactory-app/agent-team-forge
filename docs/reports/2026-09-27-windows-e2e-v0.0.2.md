# Windows e2e check of v0.0.2

This check ran on 2026-09-27 on the same Windows 11 VM as the
[v0.0.1 check](2026-09-26-windows-e2e-v0.0.1.md): 2 vCPU, 8 GB RAM, and no UAC split-token, so
everything runs at High integrity. The build is `atf-0.0.2-win-x64.zip` from the v0.0.2 release
(tag `4fee9c6`), verified against `SHA256SUMS-win-x64`
(`bf1b6601c77e98f41b1ed8fe634575c1b24f8065d4e7158076e1171cc37c2452`), which reports `atf 0.0.2`. It was installed with
`atf setup --mode wt --apply`. All tests except the install used a throwaway state directory
(`atf init` plus a copy of the real `launch-mode.json`, web port 8766). The test folders were
under a new root outside every trusted path. Pi is not installed.

To make the Claude checks real, `skipDangerousModePermissionPrompt` in `~/.claude/settings.json`
was set to `false` during the Claude tests and restored afterwards. The v0.0.1 check could not
observe the bypass warning because this setting was `true`.

## A. A client disconnecting early kills the daemon (Windows pipe accept loop)

`IpcServer.ServeWindowsAsync` only catches `OperationCanceledException` around
`pipe.WaitForConnectionAsync`. If a client connects and closes before the server instance has
accepted (Windows `ERROR_NO_DATA`), the call throws
`System.IO.IOException: The pipe is being closed`. The serving task faults, and then:

1. `DaemonCommand` sees `Task.WhenAny(serving, dispatching)` return with the lifetime not
   cancelled, and logs `error: dispatcher_halted reason=dispatcher_fault; admission stopped`.
   That message is misleading: the dispatcher did not fault.
2. `await serving` rethrows, and the process dies with an unhandled exception (visible only on
   stderr, not in `daemon.log`):

   ```
   Unhandled exception. System.IO.IOException: Denna pipe håller på att stängas.
      at System.IO.Pipes.NamedPipeServerStream.WaitForConnectionAsync(CancellationToken)
      at AgentTeamForge.Host.Transport.IpcServer.ServeWindowsAsync(CancellationToken) in …\IpcServer.cs:line 90
      at AgentTeamForge.Host.Hosting.DaemonCommand.RunAsync(…) in …\DaemonCommand.cs:line 254
   ```

3. The next client lazily starts a new daemon, and recovery quarantines every in-flight job as
   `needs_reconciliation`/`daemon_restart_uncertain`, even when the agent finished. For example,
   the `…\ATF E2e Mixed\Sub Dir` Codex rollout ends with `E2E-CODEX-MIXED-OK`, yet the job was
   quarantined.

**Reproduction without any agent:** a loop of `atf client list --state-dir X --limit 1` against
an idle daemon killed it on call 23. During the e2e run it hit 5 times, usually on the first
`client get` after a submit, and it made the first three spaces-in-cwd Codex runs look like a
path bug. Without polling, the same kind of cwd passes (item 1). The bug is unchanged on
`origin/main` `382a600`.

Suggested fix: catch `IOException` (and probably any non-fatal exception) around
`WaitForConnectionAsync`, dispose that instance and continue the loop. Also log a serving fault
as such instead of `dispatcher_halted`, and write it to `daemon.log`. A test can close a raw
client handle right after `CreateFile` in a tight loop.

## B. A bogus agent binary does not fail the job

The daemon was started with `PATH` beginning with a folder holding an invalid `claude.exe`
(4 bytes, `MZ\0\0`). The wrapper's `[System.Diagnostics.Process]::Start` failed at once in the
tab (`Win32Exception: The specified executable is not a valid application for this OS
platform`, `process exited with code 1`). The job still waited out the full startup bound, then
ended `needs_reconciliation`/`interactive_delivery_not_confirmed` after 186 s.

The PID sidecar is written before the agent starts, so `AwaitTabAsync` succeeds. The tab
survives the 2 s settle check, and the evidence loop in `WtInteractiveBackend.ReadEvidenceAsync`
only checks `tabs.IsAlive` after acknowledgement. Suggested fix: have the wrapper record a
start failure (exit code or error file) that the backend turns into `failed` with a
`launch_failed` reason. Checking `IsAlive` before the ack also works, since the tab is gone once
the wrapper exits (Windows Terminal kept the dead tab open with "press Enter to restart").
Resolving and validating the binary in `Preflight` would catch the missing and invalid cases
before any tab opens.

## C. Claude's login or first-run screen is not detected in wt

The daemon was started with `CLAUDE_CONFIG_DIR` pointing at an empty folder. Claude showed its
first-run screen ("Let's get started. Choose the text style…"), and the job stayed
`running`/`starting` at 20, 40, 60, 90 and 120 s. It then ended
`needs_reconciliation`/`interactive_delivery_not_confirmed` at 183 s. No
`agent_first_run_required` or `agent_login_required` was produced. In a first attempt the
operator completed the login by hand and the job then completed. The detection appears to rely
on reading the terminal screen, which the Herdr path can do and the wt path cannot. A wt option
could check Claude's config (`.claude.json` without `hasCompletedOnboarding`, or no
`.credentials.json`) before launch, as a preflight.

## D. Minor findings

- **Orphaned Codex processes:** after the daemon crashes from A and after `atf stop`, four
  `codex.exe` processes from finished or quarantined jobs were still running with their wrapper
  parent gone. They kept their cwd locked, and one belonged to a completed job. `atf stop` also
  printed raw `taskkill` output, including `could not be terminated` lines.
- **`setup --check` with legacy state** exits 1 with a warning, while apply mode exits 64. That
  is probably intended, but the check output also reports `claude: failed (MCP registration
  missing or stale)`, which is noise in this case.
